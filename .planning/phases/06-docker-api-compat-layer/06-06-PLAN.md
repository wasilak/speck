<objective>
Implement bind-mount support via VirtioFS: multiple VZVirtioFileSystemDeviceConfiguration devices assembled before VM start; vminitd auto-mounts tagged filesystems at boot. Ryuk's Docker socket access is handled by VirtioFS-mounting $SPECK_HOME at /var/run/ inside containers that request a Docker socket volume. Named volumes are directory-backed on the data disk.

Purpose: Satisfies STORAGE-01 (bind mounts), STORAGE-02 (uid/gid passthrough — VirtioFS default), STORAGE-03 (named volumes), STORAGE-04 (benchmark placeholder), and DOCKER-04 (Ryuk socket access). All mounts must be declared in GuestConfig before VM start — consistent with Pitfall 3.

Output: virtiofs.rs (device assembly + tag validation + cmdline arg builder); GuestConfig.volume_mounts; vminitd VirtioFS mount loop + named volume dirs + Ryuk symlink.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host_path in VolumeMountConfig → VZSharedDirectory | Host filesystem path is shared into the guest; path traversal here exposes host files |
| docker.sock symlink in /var/run/ → Speck socket | Container processes can connect to the Docker socket via the mounted path |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06-06-01 | Tampering | VirtioFS host_path path traversal (-v /../../../etc:/etc) | mitigate | config.rs validate() canonicalizes host_path (std::fs::canonicalize) and rejects if result is outside user-specified allowed roots; also rejects any container_path with ".." components |
| T-06-06-02 | Elevation of Privilege | docker.sock accessible inside containers (Ryuk) | accept | By design per D-14; the Docker socket gives container-level access to the Speck daemon, not host root. Socket is mode 0600 on the host; inside the container it is only accessible via the VirtioFS mount which is controlled by the spk run invocation. |
| T-06-06-03 | Tampering | VirtioFS tag injection via volume name | mitigate | Tags are generated as "speck-vol-{i}" where i is the index — user cannot influence the tag value. Container paths are passed to vminitd via cmdline as a structured key=value; vminitd parse function expects only [a-zA-Z0-9_/-] characters in container paths. |
| T-06-06-04 | Tampering | Named volume dir creation in /rootfs | accept | vminitd creates dirs only inside /rootfs; it is PID 1 inside the VM guest; no host filesystem access from this code path |
| T-06-06-05 | Information Disclosure | speck_home_path in kernel cmdline | accept | Kernel cmdline visible in /proc/cmdline inside the VM guest; the path value is the SPECK_HOME directory which is not sensitive |
</threat_model>
