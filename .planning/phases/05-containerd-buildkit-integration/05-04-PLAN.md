In `crates/speck-vz/src/vm_thread.rs`:

1. Add `WaitForGuestReady` to the `VmCommand` enum after `DnsVsockFd`:
   `WaitForGuestReady { ready_vsock_port: u32, reply: oneshot::Sender&lt;std::result::Result&lt;(), Error&gt;&gt; }`

2. Add match arm in the `while let Some(cmd)` loop after the `DnsVsockFd` arm:
   `VmCommand::WaitForGuestReady { ready_vsock_port, reply } => {`
   `    let control = Arc::clone(&control);`
   `    let q = queue.clone();`
   `    let result = Self::do_wait_for_ready(&control, &q, ready_vsock_port);`
   `    let _ = reply.send(result);`
   `}`

3. Add private function `do_wait_for_ready`:
   Signature: `fn do_wait_for_ready(control: &Arc&lt;Mutex&lt;VmControl&gt;&gt;, queue: &DispatchQueue, ready_vsock_port: u32) -> Result&lt;(), Error&gt;`

   Behavior:
   - Retry loop up to 30 iterations:
     a. Call `Self::do_vsock_connect(control, queue, ready_vsock_port)`
     b. On `Ok(sock)`: read exactly 6 bytes into `buf: [u8; 6]` using `sock.read(&mut buf[n..])` in a loop (until n == 6 or error). Compare buf to `b"READY\n"`. If equal: return `Ok(())`. Otherwise: return `Err(Error::VsockConnect("unexpected READY signal".into()))`.
     c. On `Err(Error::VsockConnect(_))` or `Err(Error::VsockTimeout)`: `std::thread::sleep(Duration::from_millis(200))`, continue.
     d. On other errors: return immediately.
   - After 30 failed attempts: return `Err(Error::GuestReadyTimeout)`
   - The Duration::from_millis(200) sleep and 30-attempt limit mean the host waits up to ~6 seconds for vminitd to boot and signal ready. This accommodates typical VM boot + containerd startup time.

4. Add public method `wait_for_ready`:
   `pub fn wait_for_ready(&self, ready_vsock_port: u32) -> std::result::Result&lt;(), Error&gt; {`
   `    let (tx, rx) = oneshot::channel();`
   `    self.send_blocking(VmCommand::WaitForGuestReady { ready_vsock_port, reply: tx }, rx)?`
   `}`

   (The trailing `?` propagates nested Result. This follows the pattern of `vsock_connect`, `netstack_fd`, `dns_vsock_fd`.)

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host VM config → VZVirtioBlockDeviceConfiguration | A path from GuestConfig is passed as a raw NSURL to Virtualization.framework. A crafted path could reference an unintended file. |
| vsock READY port | The host connects to a guest vsock port and trusts the b"READY\n" signal. A compromised guest could send a false READY before containerd is actually ready. |
| cargo package install | containerd-client 0.9.0 is added to Cargo.toml dev-dependencies as an [ASSUMED] package. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-04-01 | Tampering | GuestConfig disk path → VZDiskImageStorageDeviceAttachment | mitigate | GuestConfig::validate() (Plan 05-01) checks disk paths exist before VM start. The NSURL is constructed from a validated, developer-controlled path — no user input injection possible. |
| T-05-04-02 | Spoofing | READY vsock signal (b"READY\n") | accept | The guest is trusted within the VM boundary. A compromised guest could lie about READY, but that would only affect the developer's own VM boot. Production hardening (e.g., cryptographic attestation) is a v2 concern. |
| T-05-04-03 | Denial of Service | WaitForGuestReady blocks indefinitely | mitigate | do_wait_for_ready has a hard limit of 30 attempts × 200ms = 6 seconds max, then returns GuestReadyTimeout. The VmThread is not blocked; the WaitForGuestReady command runs in the vm thread's own event loop. |
| T-05-SC | Tampering | containerd-client 0.9.0 cargo install [ASSUMED] | mitigate | Blocking checkpoint:human-verify task (Task 1) requires human confirmation of package ownership before Cargo.toml is updated. Slopcheck unavailable at research time; human inspection of crates.io is the fallback. |
</threat_model>
