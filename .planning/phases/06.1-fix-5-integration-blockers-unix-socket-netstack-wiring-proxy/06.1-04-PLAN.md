<objective>
Fix CR-01 (BLOCKER): `run_up` is declared `async fn` and executes on the `#[tokio::main]` thread. Every call to `Guest::start()`, `Guest::wait_for_ready()`, `Guest::set_port_map_channel()`, `Guest::netstack_fd()`, and `Guest::dns_vsock_fd()` routes through `VmThread::send_blocking` → `tokio::sync::mpsc::Sender::blocking_send` → `tokio-1.52.3/src/future/block_on.rs` → `try_enter_blocking_region().expect(...)` → panic "Cannot block the current thread from within a runtime". This panic fires on the very first call before any of the five phase-06.1 fixes can be exercised.

Fix path A (minimal): Wrap the synchronous VM control sequence in `tokio::task::spawn_blocking`. The blocking closure owns `config`, constructs `Guest`, calls all five blocking methods, and returns `(guest, netstack_fd, dns_vsock_fd, port_map_rx)`. The outer async function extracts this tuple via `.await??` and continues with `SpeckNet::spawn` and `SpeckDockerd::start`.

Purpose: This is the sole runtime blocker. All structural fixes from plans 06.1-01 through 06.1-03 are unreachable until this panic is eliminated.

Output: `crates/speck-cli/src/commands/up.rs` with the spawn_blocking pattern applied around lines 50–66. No other file changes.
</objective>

    - Construct `speck_vz::Guest::new(config)` as a local `guest`

    The outer async code unwraps with `.await??` (first `?` unwraps `JoinError` from `spawn_blocking`, second `?` propagates the `anyhow::Result` from the closure). Destructure the result tuple as:
    `let (guest, netstack_fd, dns_vsock_fd, port_map_rx) = ...`

    The spinner (`ProgressBar`) stays outside the closure (created before, `finish_with_message` called after the spawn_blocking block). The spinner's interim message ("Waiting for guest...") can be set before the spawn_blocking call since the spinner is already in steady-tick mode.
