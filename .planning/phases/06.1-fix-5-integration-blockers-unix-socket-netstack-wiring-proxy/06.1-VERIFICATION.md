## Gaps Summary

### CR-01: runtime panic in run_up (BLOCKER)

Every `Guest` control method called from `up.rs` routes through `VmThread::send_blocking`, which
calls `tokio::sync::mpsc::Sender::blocking_send`. That delegates to `crate::future::block_on`
(confirmed in tokio 1.52.3 source at
`/Users/piotrek/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/tokio-1.52.3/src/future/block_on.rs`
line 6), which calls `try_enter_blocking_region().expect("Cannot block the current thread from
within a runtime...")`. Because `run_up` is an `async fn` running inside `#[tokio::main]`,
`try_enter_blocking_region` finds an active runtime handle and panics.

The panic fires on the FIRST call — `guest.start()?` at line 55 — before any of the five bug
fixes can be exercised. None of the structural improvements (proxy loop, VirtioFS, netstack
wiring, port bindings) are reachable at runtime.

**Fix path A (minimal):** Wrap the synchronous VM control sequence in `tokio::task::spawn_blocking`:
```rust
let (guest, netstack_fd, dns_vsock_fd, port_map_rx) =
    tokio::task::spawn_blocking(move || -> anyhow::Result<_> {
        let guest = speck_vz::Guest::new(config);
        guest.start()?;
        guest.wait_for_ready()?;
        let (port_map_tx, port_map_rx) = tokio::sync::mpsc::channel(64);
        guest.set_port_map_channel(port_map_tx)?;
        let netstack_fd = guest.netstack_fd()?;
        let dns_vsock_fd = guest.dns_vsock_fd().ok();
        Ok((guest, netstack_fd, dns_vsock_fd, port_map_rx))
    })
    .await??;
```

**Fix path B (structural):** Convert `VmThread::send_blocking` / `Guest` public methods to
`async fn`, replacing `blocking_send`/`blocking_recv` with `sender.send().await` and
`rx.await`. This is the idiomatic tokio approach but requires touching more files.

### CR-02: _delegate_rx dropped immediately (WARNING)

`do_start` creates a `std::sync::mpsc::channel::<VmStateEvent>()` but the receiver `_delegate_rx`
is a local variable that drops when `do_start` returns (line 481). All VM state notifications
(crash, OOM, kernel panic) are silently dropped. `VmControl.state` never transitions from
`Running` on unplanned termination. This is not a startup blocker, but a correctness gap
that prevents health-check loops and the Docker API `/info` path from detecting VM death.

### CR-03: Missing objc2-virtualization feature flags (WARNING)

`crates/speck-vz/Cargo.toml` lists `"VZBootLoader"` and `"VZPlatformConfiguration"` but
`vm_thread.rs` imports and calls `VZLinuxBootLoader`, `VZGenericPlatformConfiguration`,
`VZVirtioEntropyDeviceConfiguration`, and `VZEntropyDeviceConfiguration` — none of which
have matching feature entries. The crate currently compiles because feature cascading happens
to include them transitively. A patch release of `objc2-virtualization` that reorganises
feature deps could break the build without any change to this codebase.
