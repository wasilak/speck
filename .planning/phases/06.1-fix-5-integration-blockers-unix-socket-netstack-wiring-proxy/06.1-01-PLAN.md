<objective>
Fix Bug 1 (proxy loop exits after first client) and Bug 5 (VirtioFS gated incorrectly), and add the VmThread helpers required by Bug 2's netstack wiring (Plan 06.1-02).

Purpose: After Phase 6, `containerd_unix_proxy()` and `buildkitd_unix_proxy()` accept one Unix client and then drop the listener. Every subsequent Docker API request to a container gets ECONNREFUSED. VirtioFS is never configured because neither volume mounts nor network is set in the current up.rs. These two bugs mean the system cannot serve more than one container API request and has no shared filesystem.

Output:
- `vm_thread.rs`: `clone_cmd_sender()` pub(crate) helper, `SetPortMapChannel` VmCommand variant with handler, `VmThread::set_port_map_channel()` public method, virtiofs gate removed from `do_start`
- `guest.rs`: `vsock_connector_for_port()` private helper, loop-based `containerd_unix_proxy()` and `buildkitd_unix_proxy()`, `Guest::set_port_map_channel()` delegation method
</objective>

       Body: clone `self.thread.clone_cmd_sender()` into a local `sender`, then return a move closure that creates a oneshot channel, sends `VmCommand::VsockConnect { port, reply: tx }` via `sender.blocking_send(...)`, and returns the result from `rx.blocking_recv()`. <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UnixListener (proxy) → host process | Any local user process can connect to the proxy socket in /tmp; the socket uses a PID-unique name to reduce collision risk |
| VsockConnect closure → VmThread channel | The connector closure sends blocking commands from std::thread context; panics if called from an async task |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-06.1-01 | Spoofing | containerd/buildkitd proxy Unix sockets in /tmp | accept | Sockets are PID-unique (`speck-containerd-<pid>-<port>.sock`); macOS enforces same-user path isolation; no auth beyond Unix permissions needed at v1 |
| T-06.1-02 | Tampering | vsock_connector_for_port closure called from tokio task | mitigate | Document in action and code comment: closure must only be called from `std::thread::spawn` (OS thread); proxy spawn already uses `std::thread::spawn`, not `tokio::task::spawn` |
| T-06.1-03 | Denial of Service | loop listener.accept() — malicious flood of connections | accept | macOS backlog limits TCP SYN floods; Unix socket backlog is OS-controlled; v1 single-VM scope |
</threat_model>
