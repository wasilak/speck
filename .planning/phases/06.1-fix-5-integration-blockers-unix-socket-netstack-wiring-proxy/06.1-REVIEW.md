# Phase 06.1: Code Review Report

**Reviewed:** 2026-06-28
**Depth:** standard
**Files Reviewed:** 6
**Status:** issues_found

## Summary

This phase fixes five integration blockers in the Speck runtime: proxy loop continuity, netstack spawning, speck_home creation, port binding parsing, and VirtioFS gating. The proxy loop (Bug 1) and VirtioFS gate removal (Bug 5) are correctly fixed. The port-binding label roundtrip (Bug 4) is structurally sound. However, three BLOCKER-level defects were found alongside five warnings that collectively threaten runtime stability and correctness.

The most severe issue is that every synchronous `Guest` method in `up.rs` calls `tokio::sync::mpsc::Sender::blocking_send` and `tokio::sync::oneshot::Receiver::blocking_recv` from within an async tokio task. Both functions are documented to panic in that context. The process will hard-crash on the first invocation of `spk up`. The second blocker — an immediately dropped channel receiver in `do_start` — means spontaneous VM termination (kernel panic, OOM) can never update the visible state, leaving the runtime stuck reporting `Running` forever. A third missing-feature issue in `Cargo.toml` would prevent the crate from compiling at all if the objc2-virtualization feature graph does not cascade the missing entries.

## Critical Issues

### CR-01: `blocking_send`/`blocking_recv` called inside async tokio task — hard panic at startup

**File:** `crates/speck-cli/src/commands/up.rs:55-66`

**Issue:** `run_up` is an `async fn` called via `#[tokio::main]` (confirmed in `crates/speck-cli/src/main.rs:118,128`). Every call below delegates to `VmThread::send_blocking`, which calls `tokio::sync::mpsc::Sender::blocking_send` and `tokio::sync::oneshot::Receiver::blocking_recv`. Both are documented to panic when called inside an asynchronous execution context:

```
guest.start()?;            // → blocking_send + blocking_recv — PANIC
guest.wait_for_ready()?;   // → blocking_send + blocking_recv — PANIC
guest.set_port_map_channel(port_map_tx)?;  // same
let netstack_fd = guest.netstack_fd()?;    // same
let dns_vsock_fd = guest.dns_vsock_fd().ok(); // same
```

The code in `guest.rs` already acknowledges the constraint in a comment for `vsock_connector_for_port` (line 94-95: "must NOT be called from an async task because `blocking_send` / `blocking_recv` will panic inside a tokio executor"), but the same constraint was not applied to the `Guest` public API called from `run_up`.

**Fix:** Wrap the synchronous startup sequence in `tokio::task::spawn_blocking`:

```rust
pub async fn run_up(args: UpArgs, speck_home: &Path) -> anyhow::Result<()> {
    // ... path setup ...
    let speck_home = speck_home.to_owned();
    let (guest, netstack_fd, dns_vsock_fd, port_map_rx) =
        tokio::task::spawn_blocking(move || -> anyhow::Result<_> {
            let guest = speck_vz::Guest::new(config);
            guest.start()?;
            guest.wait_for_ready()?;
            let (port_map_tx, port_map_rx) =
                tokio::sync::mpsc::channel::<speck_net::PortMapConfig>(64);
            guest.set_port_map_channel(port_map_tx)?;
            let netstack_fd = guest.netstack_fd()?;
            let dns_vsock_fd = guest.dns_vsock_fd().ok();
            Ok((guest, netstack_fd, dns_vsock_fd, port_map_rx))
        })
        .await??;
    // continue with async SpeckNet and DockerD setup
}
```

Alternatively, make `Guest::start`, `Guest::wait_for_ready`, and the fd accessors properly async by using `tokio::sync::mpsc::Sender::send().await` and removing `blocking_send`/`blocking_recv` from the `VmThread` API surface.

### CR-02: `_delegate_rx` dropped immediately — VM crash leaves state permanently `Running`

**File:** `crates/speck-vz/src/vm_thread.rs:481-482`

**Issue:** In `do_start`, the std-channel receiver is immediately bound with a discard-binding and goes out of scope at the end of `do_start`:

```rust
let (delegate_tx, _delegate_rx) = std::sync::mpsc::channel::<VmStateEvent>();
let delegate = VmDelegate::create(delegate_tx);
```

`_delegate_rx` drops when `do_start` returns. Because `delegate_tx` now has no living receiver, every `delegate_tx.send(VmStateEvent)` inside `VmDelegate` silently returns `Err(SendError)`. The `VmDelegate` is registered on the VM object and retained by Obj-C ARC, so the delegate itself stays alive — but all state-change notifications (VM stopped unexpectedly, kernel panic, OOM kill) are silently discarded.

Consequence: `VmControl.state` is never updated from `Running` on unplanned termination. `guest.state()` returns `Running` indefinitely. A caller that polls state to detect VM death (e.g., a health-check loop or the Docker API's `/info` path) will never see the transition.

**Fix:** Move `_delegate_rx` into the long-lived `VmControl` struct so the channel stays open for the lifetime of the VM:

```rust
struct VmControl {
    state: InternalState,
    machine: VmMachine,
    socket_device: VmSocketDevice,
    netstack_fd: Option<RawFd>,
    dns_vsock_fd: Option<RawFd>,
    port_maps: Vec<PortMapConfig>,
    port_map_tx: Option<mpsc::Sender<PortMapConfig>>,
    // Add:
    _delegate_rx: Option<std::sync::mpsc::Receiver<VmStateEvent>>,
}
```

And in `do_start`, after creating the delegate:
```rust
let (delegate_tx, delegate_rx) = std::sync::mpsc::channel::<VmStateEvent>();
let delegate = VmDelegate::create(delegate_tx);
// ...
ctrl._delegate_rx = Some(delegate_rx); // keeps channel alive
```

The VM command loop can then drain `delegate_rx` as part of its select/poll or spawn a watcher thread that transitions `VmControl.state` to `Stopped` on reception.

### CR-03: Missing objc2-virtualization feature flags — potential compile failure

**File:** `crates/speck-vz/Cargo.toml:13-39`

**Issue:** `vm_thread.rs` imports and directly calls methods on four Obj-C classes that have no corresponding feature flag in the `objc2-virtualization` dependency:

| Class used in `vm_thread.rs` | Expected feature flag | Present in `Cargo.toml`? |
|---|---|---|
| `VZLinuxBootLoader` (line 17, line 325) | `"VZLinuxBootLoader"` | No — only `"VZBootLoader"` |
| `VZGenericPlatformConfiguration` (line 367) | `"VZGenericPlatformConfiguration"` | No — only `"VZPlatformConfiguration"` |
| `VZVirtioEntropyDeviceConfiguration` (line 370) | `"VZVirtioEntropyDeviceConfiguration"` | No |
| `VZEntropyDeviceConfiguration` (line 373) | `"VZEntropyDeviceConfiguration"` | No |

In the `objc2` ecosystem, features are per-class and subclass features are not automatically included by their parent-class feature. If the crate's internal feature graph does not cascade these, the crate will fail to compile with "use of undeclared type" errors. Even if the build happens to succeed today through an undocumented transitive dependency, it is brittle: a patch release of `objc2-virtualization` could reorganize feature deps and break the build without any change to this codebase.

**Fix:** Add the four missing features to `Cargo.toml`:

```toml
objc2-virtualization = { version = "0.3", features = [
    # ... existing features ...
    "VZLinuxBootLoader",
    "VZGenericPlatformConfiguration",
    "VZVirtioEntropyDeviceConfiguration",
    "VZEntropyDeviceConfiguration",
] }
```

## Warnings

### WR-01: Empty `PathBuf` written as `initrd_path = Some("")` when no initrd file exists

**File:** `crates/speck-cli/src/commands/up.rs:22-27, 39`

**Issue:** When neither `--initrd` is provided nor `speck_home/initrd` exists on disk, `initrd_path` is set to `PathBuf::default()` (the empty path):

```rust
let initrd_path: std::path::PathBuf = args
    .initrd
    .clone()
    .or_else(|| {
        let p = speck_home.join("initrd");
        if p.exists() { Some(p) } else { None }
    })
    .unwrap_or_default();   // <-- empty PathBuf when no initrd found
```

`GuestConfigBuilder::initrd_path` (confirmed in `config.rs:294-296`) unconditionally wraps any value: `self.initrd_path = Some(path.into())`. So `Some(PathBuf::from(""))` is stored and later evaluated by `GuestConfig::validate()` (config.rs:170-174):

```rust
if let Some(ref initrd) = self.initrd_path && !initrd.exists() {
    return Err(format!("initrd not found: {}", initrd.display()));
}
```

An empty path does not exist, so every `spk up` invocation where no initrd file is present fails with `"initrd not found: "` — even when the kernel boots from a block device and an initrd is not required.

**Fix:** Keep the type as `Option<PathBuf>` and only call `.initrd_path()` on the builder when `Some`:

```rust
let initrd_path: Option<std::path::PathBuf> = args
    .initrd
    .clone()
    .or_else(|| {
        let p = speck_home.join("initrd");
        if p.exists() { Some(p) } else { None }
    });

let mut builder = GuestConfig::builder()
    .kernel_path(kernel_path)
    // ...
let config = if let Some(ip) = initrd_path {
    builder.initrd_path(ip)
} else {
    builder
}.build();
```

### WR-02: `stream.try_clone().expect()` panics on OS error in bridge proxy threads

**File:** `crates/speck-vz/src/guest.rs:246`

**Issue:** In `bridge_vsock_unix`, called once per accepted proxy client in a `std::thread::spawn` thread:

```rust
let stream_clone = stream.try_clone().expect("clone unix stream");
```

`try_clone()` performs an `fcntl(F_DUPFD)` syscall. Under fd exhaustion (`EMFILE`/`ENFILE`) or a rare kernel error, it returns `Err`. The `expect` panics. Thread panics in Rust are not propagated to the caller — the thread silently dies. The Unix stream fd is then also dropped, closing the client connection without sending an error. Worse, the vsock fd (already duped on line 240) leaks because the `dup_fd`/`vsock_dup` holding it is dropped mid-way through the function, but only after the spawn for the other direction might or might not have occurred.

**Fix:** Replace with explicit error handling and early return:

```rust
let stream_clone = match stream.try_clone() {
    Ok(s) => s,
    Err(e) => {
        tracing::warn!(error = %e, "failed to clone unix stream in vsock bridge; dropping client");
        return;
    }
};
```

### WR-03: `do_wait_for_ready` holds command loop hostage for up to 15 minutes in the worst case

**File:** `crates/speck-vz/src/vm_thread.rs:755-785`

**Issue:** The command loop (`while let Some(cmd) = rx.blocking_recv()`) is single-threaded. `VmCommand::WaitForGuestReady` calls `do_wait_for_ready` inline:

```rust
VmCommand::WaitForGuestReady { ready_vsock_port, reply } => {
    let result = Self::do_wait_for_ready(&control, &q, ready_vsock_port);
    let _ = reply.send(result);
}
```

`do_wait_for_ready` loops up to 30 times, each iteration calling `do_vsock_connect` which has a `recv_timeout(Duration::from_secs(30))` wait (line 745). In the degenerate case where every vsock connect attempt times out (as opposed to fast-failing with ECONNREFUSED), the command loop is blocked for 30 × 30 s = 900 seconds. During this period, no other commands — including `VmCommand::Shutdown` — can be processed.

Even in the fast-fail case (ECONNREFUSED), each iteration still calls `thread::sleep(200ms)`, pinning the loop for 30 × 200 ms = 6 seconds. This is enough to starve any concurrent stop/state queries.

**Fix:** Spawn `do_wait_for_ready` on a dedicated `std::thread` and have it send the result back via the reply sender, allowing the command loop to continue servicing other commands:

```rust
VmCommand::WaitForGuestReady { ready_vsock_port, reply } => {
    let control = Arc::clone(&control);
    let q = queue.clone();
    std::thread::spawn(move || {
        let result = Self::do_wait_for_ready(&control, &q, ready_vsock_port);
        let _ = reply.send(result);
    });
}
```

### WR-04: `bridge_vsock_unix` does not propagate half-close — connections can hang

**File:** `crates/speck-vz/src/guest.rs:249-283`

**Issue:** The bidirectional bridge spawns one thread for vsock→unix and handles unix→vsock in the current thread. When the vsock→unix direction ends (EOF or error), the spawned thread exits and drops `stream_clone` (the unix write handle). However, the current thread continues blocking in `stream_read.read(...)` waiting for more data from the unix client. If the unix client is doing a half-close (it has finished writing but is still waiting to read a response), the current thread will block indefinitely. The mirror case — the unix client closes its write end — does not send a `shutdown(SHUT_WR)` to the vsock side, so the guest may never see EOF.

**Fix:** After either direction terminates, signal the other direction to stop via `UnixStream::shutdown(Shutdown::Both)` on the stream and a write of zero bytes or shutdown on the vsock side:

```rust
// After vsock→unix thread finishes:
let _ = stream_clone_for_signal.shutdown(std::net::Shutdown::Both);

// After unix→vsock loop exits (current thread):
// vsock_dup drops here, closing the vsock fd, which signals the guest.
```

### WR-05: `dup_host_fd` raw fd leaked on failed VM start after network socket setup

**File:** `crates/speck-vz/src/vm_thread.rs:435-510`

**Issue:** Inside `do_start`, after the network socketpair is set up:

```rust
let d = libc::dup(host_fd);
if d < 0 { return Err(...); }
dup_host_fd = Some(d);
```

If `do_start` returns an error at any point between here and the storage in `ctrl.netstack_fd` (line 509), `d` is a `RawFd` (i32) that is never closed. Rust does not implement `Drop` for `RawFd`, so the fd leaks. The failure points include `vm_config.validateWithError()` (line 470), and anything in between. In a retry-heavy startup scenario (broken kernel image, misconfigured initrd), each failed attempt leaks one fd.

**Fix:** Wrap the duplicated fd in a guard that closes on drop if not consumed:

```rust
struct FdGuard(RawFd);
impl Drop for FdGuard { fn drop(&mut self) { unsafe { libc::close(self.0); } } }
impl FdGuard { fn take(mut self) -> RawFd { let fd = self.0; self.0 = -1; fd } }

let dup_host_fd_guard = FdGuard(d);
// ... on success path:
ctrl.netstack_fd = Some(dup_host_fd_guard.take());
// On any error path: guard drops and closes fd automatically.
```

### IN-01: Duplicate `NetworkConfig::default()` — two independent instances with divergent potential

**File:** `crates/speck-cli/src/commands/up.rs:47, 64`

**Issue:** Two separate `NetworkConfig::default()` instances are created: one passed into `GuestConfig::builder().network(NetworkConfig::default())` (line 47) and a second into `speck_net::SpeckNet::new(net_config, Some(53))` (line 64). If `NetworkConfig::default()` ever gains fields with meaningful defaults (e.g., MTU, subnet hint), the two instances could silently diverge, causing the netstack to use different settings than the VM was configured with.

**Fix:** Derive the config once and clone it:
```rust
let net_config = speck_net::config::NetworkConfig::default();
let config = GuestConfig::builder()
    .network(net_config.clone())
    // ...
let _netstack_handles = speck_net::SpeckNet::new(net_config, Some(53)).spawn(...);
```

### IN-02: DNS vsock port 53 is a magic number duplicated in two separate call sites

**File:** `crates/speck-cli/src/commands/up.rs:47, 65`

**Issue:** The vsock port used for the DNS proxy (53) is hardcoded at both the GuestConfig builder call (`.dns_vsock_port(53)`) and the SpeckNet constructor (`SpeckNet::new(net_config, Some(53))`). These two must stay in sync; they will silently diverge if one is updated without the other.

**Fix:** Define a named constant:
```rust
const DNS_VSOCK_PORT: u32 = 53;
```
and reference it in both places.

### IN-03: `logs()`, `archive()`, `put_archive()` return 501 — required for testcontainers per CLAUDE.md

**File:** `crates/speck-dockerd/src/handlers/containers.rs:308-318`

**Issue:** The three Docker API endpoints `GET /containers/{id}/logs`, `GET /containers/{id}/archive`, and `PUT /containers/{id}/archive` return `501 Not Implemented`. Per CLAUDE.md's table of required endpoints, `archive` (copy-in/out) is listed as "testcontainers copies files in" — a hard requirement for testcontainers compatibility. Without it, testcontainers integration tests that copy fixtures into containers will fail with 501. The current stubs will not surface a clear error in automated test runs; callers receive no response body.

**Fix:** Implement at minimum the `GET /containers/{id}/archive` path (tar stream of a container path). Log a `TODO` comment at the stub site with a tracking reference so it is not lost:
```rust
pub async fn archive() -> StatusCode {
    // TODO(issue #XX): implement GET /containers/{id}/archive for testcontainers copy-in support
    StatusCode::NOT_IMPLEMENTED
}
```
