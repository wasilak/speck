<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 3: DNS-03 — Verify container DNS works while Cloudflare WARP is active</name>
  <read_first>
    - .planning/phases/11-vpn-proof-dns/11-RESEARCH.md — DNS-03 analysis: WARP registers 127.0.2.2/3 as system resolver via SCDynamicStore; getaddrinfo on host uses these automatically; no WARP-specific code needed
  </read_first>
  <what-built>
    The Phase 11 DNS proxy routes non-VPN queries through getaddrinfo on the macOS host. When
    Cloudflare WARP is active, WARP registers its resolvers (127.0.2.2 and 127.0.2.3) with the
    macOS system resolver via SCDynamicStore. getaddrinfo picks these up automatically. As a
    result, container DNS queries that pass through the vsock proxy to getaddrinfo will resolve
    through WARP's resolver without any special code.

    If WARP is not installed, this test can be substituted with a corporate VPN that has a
    custom DNS resolver — the behavior is equivalent.
  </what-built>
  <how-to-verify>
    Step 1: Enable Cloudflare WARP (or connect to corporate VPN).
    Confirm WARP/VPN is active: the WARP icon in the menu bar shows "Connected", or VPN shows
    the connected state.

    Step 2: Start Speck if not already running:
      ./target/debug/spk up --foreground &amp;
    Wait for startup.

    Step 3: Run a container and test DNS from inside:
      ./target/debug/spk run alpine nslookup google.com
    or:
      docker run --rm alpine nslookup google.com
    (docker pointing to Speck's socket via DOCKER_HOST)

    Expected: nslookup returns one or more A records for google.com. The query must succeed
    (exit 0), not timeout or return SERVFAIL.

    Step 4: Optionally confirm which resolver answered:
      ./target/debug/spk run alpine nslookup google.com 127.0.0.1
    (querying the guest's local DNS forwarder directly)
    Expected: same successful result.

    If WARP is not available: run the same test WITHOUT WARP active (DNS-02 baseline), then
    enable a different VPN with a custom DNS, then run again. Both should succeed.
  </how-to-verify>

<task type="checkpoint:human-verify" gate="blocking">
  <name>Task 4: DNS-05 — Verify live DNS resolver update on VPN toggle (no VM restart)</name>
  <read_first>
    - .planning/phases/11-vpn-proof-dns/11-RESEARCH.md — DNS-05 analysis: SCDynamicStoreSetDispatchQueue fires the resolver_changed_cb callback on VPN toggle; tokio::sync::watch channel pushes new ResolverTable to spawn_dns_proxy; no VM restart needed
    - .planning/phases/11-vpn-proof-dns/11-03-PLAN.md — spawn_resolver_watcher implementation: GCD serial queue watcher that updates the watch channel within the SCDynamicStore notification latency (~200ms)
  </read_first>
  <what-built>
    Plan 11-03 implemented `spawn_resolver_watcher` which registers a `SCDynamicStoreSetDispatchQueue` callback. When macOS network configuration changes (VPN toggle, Wi-Fi handoff), the GCD callback fires, reads the new resolver configuration from SCDynamicStore, and sends the updated `ResolverTable` through a `tokio::sync::watch` channel. The DNS proxy in `spawn_dns_proxy` reads from this channel on each query — so the next DNS query after a VPN reconnect automatically uses the new resolver table without any VM restart.

    This is Phase 11's core live-update guarantee. Unit tests verify the ResolverTable logic, but only a real VPN toggle on a real macOS host can confirm that `SCDynamicStoreSetDispatchQueue` actually fires the GCD callback and the watch channel updates.
  </what-built>
  <how-to-verify>
    Step 1: Start Speck and confirm baseline DNS works:
      ./target/debug/spk up --foreground &amp;
      ./target/debug/spk run alpine nslookup google.com
    Expected: A records returned, exit 0.

    Step 2: Connect a VPN (corporate VPN or Cloudflare WARP with Gateway).
    Confirm the VPN is active (VPN icon in menu bar shows connected state).

    Step 3: Confirm DNS still works through VPN (tests the initial SCDynamicStore read):
      ./target/debug/spk run alpine nslookup google.com
    Expected: A records returned, exit 0.

    Step 4: Disconnect the VPN. Wait 2 seconds. Reconnect the VPN.
    The VPN reconnect is the live-update trigger — SCDynamicStore fires the notification.

    Step 5: Within 5 seconds of VPN reconnect, run from inside a container:
      ./target/debug/spk run alpine nslookup google.com
    Expected: A records returned, exit 0 — WITHOUT running `spk down &amp;&amp; spk up`.

    If the query fails or times out, check Speck logs for "resolver table updated" tracing events.
    A SERVFAIL response (not NXDOMAIN) would indicate DNS-06 is working but DNS-05 is not.

    Note: If VPN is unavailable, substitute a Wi-Fi network change (toggle Wi-Fi off then on)
    as a weaker substitute that also triggers SCDynamicStore notifications.
  </how-to-verify>
  <resume-signal>Type "DNS-05 confirmed" if nslookup succeeded within 5s of VPN reconnect without restarting Speck. Type "DNS-05 partial — VPN unavailable, Wi-Fi toggle tested instead" if a substitute test was used. Describe failures or timeouts if the check failed.</resume-signal>
