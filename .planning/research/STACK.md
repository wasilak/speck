# Technology Stack — v1.2 Hardened Runtime

**Project:** Speck (`spk`)
**Researched:** 2026-07-06
**Scope:** NEW crates only — existing v1.1 stack is validated and not re-examined.

---

## Summary

Four capability gaps drive the v1.2 additions: (1) dockerd state must survive daemon restarts — SQLite via `rusqlite`+`deadpool-sqlite` wins over `sled` (pre-1.0, on-disk format unstable, last stable release 2021) and raw JSON files (no ACID); (2) the DNS proxy and vminitd unsafe calls need unit tests — `mockall` 0.15.0 provides trait-level mocking for both, with `async_trait` 0.1.89 bridging async trait mocking; (3) Developer ID signing belongs in xtask as shell-outs to Apple's native tools (`codesign`, `xcrun notarytool`, `xcrun stapler`) with `cargo-codesign` 0.4.2 available as a thin orchestrator; (4) registry credentials need `secrecy` 0.10.3 so the password field zeroizes on drop and requires an explicit `.expose_secret()` call.

---

## 1. State Persistence — `speck-dockerd`

### Problem

`AppState` holds `container_store`, `network_store`, and `volume_store` as `Arc<Mutex<HashMap>>`. Daemon restart destroys all state. Docker Compose, testcontainers, and Ryuk all assume containers, networks, and volumes persist across restarts.

### Decision: SQLite via `rusqlite` + `deadpool-sqlite`

| Crate | Version | Purpose | Confidence |
|-------|---------|---------|-----------|
| `rusqlite` | 0.40.1 | SQLite bindings with bundled SQLite 3.53.2 | HIGH — verified crates.io, published June 2026 |
| `rusqlite_migration` | 2.6.0 | Schema migration using SQLite `user_version` — no external CLI | HIGH — verified crates.io, published May 2026 |
| `deadpool-sqlite` | 0.13.0 | Async connection pool over rusqlite via `spawn_blocking` — tokio-compatible | HIGH — verified crates.io, published Feb 2026; requires Rust 1.85, edition 2024 |

### Why not sled

`sled` stable is 0.34.7, last released September 2021. The maintainer's own README states: "sled should be considered unstable for the time being" and "the on-disk format is going to change in ways that require manual migrations before 1.0.0." There is a 1.0.0-alpha.124 (October 2024) but it is still pre-release with a changing API. The sled README explicitly recommends SQLite when reliability is the primary concern. Adopting sled for a dockerd state store would introduce a dependency with undefined upgrade guarantees.

### Why not plain JSON files

JSON files lack atomicity. Concurrent reads from `spk ps` and a running daemon write create TOCTOU races. A daemon crash mid-write silently corrupts the state file. SQLite's WAL mode handles this correctly.

### Integration pattern

`deadpool-sqlite` wraps `rusqlite::Connection` in an async pool using `spawn_blocking` internally, matching how the rest of `speck-dockerd` uses tokio. The pool is created once at daemon startup and stored in `AppState`.

```toml
# speck-dockerd/Cargo.toml
[dependencies]
rusqlite          = { version = "0.40", features = ["bundled"] }
rusqlite_migration = "2.6"
deadpool-sqlite   = "0.13"
```

Schema: three tables — `containers`, `networks`, `volumes`. Loaded into the existing `HashMap` caches at startup; written through on every mutation. WAL mode enabled at connection open via `PRAGMA journal_mode=WAL`. Database at `$SPECK_HOME/state.db`.

## 2. Unit Testing DNS Proxy — `speck-net`

### Problem

`speck-net/src/dns.rs` (449 lines) is Speck's core value proposition — the DNS proxy that survives VPN and WARP. It has zero tests. It uses tokio UDP sockets, macOS `SCDynamicStore` for live DNS server updates, and `getaddrinfo` (blocking) for resolution.

### Recommended approach: Trait abstraction + `mockall`

| Crate | Version | Purpose | Confidence |
|-------|---------|---------|-----------|
| `mockall` | 0.15.0 | `#[automock]` proc macro generates mock structs for traits | HIGH — verified crates.io, published June 2026 |
| `async-trait` | 0.1.89 | Proc macro for `async fn` in trait definitions that `mockall` can mock | HIGH — verified crates.io, published Aug 2025 |

`tokio-test` 0.4 is already in the stack's dev dependencies and covers `#[tokio::test]` and mock I/O.

### Abstraction boundary

Extract the SCDynamicStore/getaddrinfo coupling behind a `DnsBackend` trait:

```rust
#[async_trait]
#[cfg_attr(test, mockall::automock)]
pub trait DnsBackend: Send + Sync {
    async fn resolve(&self, name: &str, qtype: u16) -> Vec<std::net::IpAddr>;
    fn upstream_servers(&self) -> Vec<std::net::SocketAddr>;
}
```

- Real impl wraps `tokio::task::spawn_blocking(|| unsafe { getaddrinfo(...) })` and reads from SCDynamicStore.
- Mock impl (generated by `mockall`) returns configurable values in `#[tokio::test]` tests.
- Tests spin up a real `UdpSocket::bind("127.0.0.1:0")` — no fake transport needed.

This pattern covers: correct DNS response construction, NXDOMAIN→SERVFAIL mapping, TTL capping, round-robin server selection, and error propagation — all without a running VM or real VPN.

### mockall and async traits

`mockall` 0.15.0 requires `#[automock]` to appear **before** `#[async_trait]`. With Rust 2024 edition, you may also use `#[trait_variant::make]` (mockall 0.14.0+ supports this), but the `async_trait` path is better documented for this specific interaction and the macro has zero runtime overhead.

```toml
# speck-net/Cargo.toml
[dependencies]
async-trait = "0.1"   # needed if DnsBackend is public and used across crate boundaries

[dev-dependencies]
mockall     = "0.15"
```

## 3. Unit Testing Unsafe libc Calls — `speck-guest`

### Problem

`vminitd.rs` (1541 lines) has 10+ unsafe libc calls: `mount`, `pivot_root`, `chroot`, `sysctl`, `umount2`. These cannot be unit-tested without root privileges on an arm64 Linux kernel. Zero tests exist today.

### Recommended approach: `Syscalls` trait + `mockall` for orchestration logic

Same crates as section 2 (`mockall` 0.15.0). No additional dependencies.

The testable part of vminitd is not the syscall itself, but the **orchestration logic** — mount ordering, error handling, argument construction, sysctl value building. Extract a `Syscalls` trait:

```rust
#[cfg_attr(test, mockall::automock)]
pub(crate) trait Syscalls {
    fn mount(&self, src: &str, target: &str, fstype: &str, flags: u64, data: Option<&str>) -> std::io::Result<()>;
    fn pivot_root(&self, new_root: &str, put_old: &str) -> std::io::Result<()>;
    fn umount2(&self, target: &str, flags: libc::c_int) -> std::io::Result<()>;
    fn sysctl_write(&self, name: &str, value: &[u8]) -> std::io::Result<()>;
}
```

Real impl (`LinuxSyscalls`) contains the actual `unsafe { libc::mount(...) }` calls. Test coverage achievable without root:
- Mount sequence ordering (e.g., `/proc` before `/sys`)
- Error propagation when a mount fails (EINVAL, ENODEV)
- Correct flag construction (`MS_BIND | MS_REC`)
- sysctl value encoding
- pivot_root choreography (bind-mount new root, move old root, unmount)

The actual `libc::mount` calls can only be exercised in hardware integration tests (root + Linux required). Mark them `#[ignore]` with an explanatory comment — consistent with the existing pattern for `#[ignore]`'d VM integration tests in `speck-vz`.

Since `vminitd` targets `aarch64-unknown-linux-musl` (not macOS), `mockall` is a dev-dependency only on the guest crate.

```toml
# speck-guest/Cargo.toml
[dev-dependencies]
mockall = "0.15"
```

## 4. Developer ID Signing + Notarization — `xtask`

### Problem

Today speck is ad-hoc signed (`codesign -s -`). Ad-hoc signing carries the `com.apple.security.virtualization` entitlement for local development but cannot be notarized. Homebrew's official tap drops un-notarized casks around September 2026. v1.2 adds Developer ID + notarization.

### Recommended approach: Shell out from xtask to Apple's native tools

No new Rust crate dependencies. The `xtask` crate shells out via `std::process::Command`:

| Step | Command |
|------|---------|
| 1. Sign binary | `codesign --sign "Developer ID Application: <identity>" --entitlements speck.entitlements --options runtime --force --timestamp target/release/spk` |
| 2. Create archive | `tar -czf spk-aarch64-apple-darwin.tar.gz -C target/release spk` |
| 3. Notarize | `xcrun notarytool submit spk-aarch64-apple-darwin.tar.gz --apple-id $APPLE_ID --team-id $TEAM_ID --password $APP_SPECIFIC_PASSWORD --wait` |
| 4. Staple | `xcrun stapler staple spk-aarch64-apple-darwin.tar.gz` |

Environment variables (`APPLE_ID`, `TEAM_ID`, `APP_SPECIFIC_PASSWORD`) read from the environment — maps directly to GitHub Actions secrets for CI.

### Optional: `cargo-codesign` 0.4.2

| Tool | Version | Purpose | Confidence |
|------|---------|---------|-----------|
| `cargo-codesign` (external install) | 0.4.2 | Orchestrates codesign → notarytool → stapler in one command; reads credentials from `sign.toml` | MEDIUM — verified crates.io June 2026; macOS path described as battle-tested; external install, not a Cargo dependency |

`cargo-codesign` is installed separately (`cargo install cargo-codesign`) and can be invoked from xtask via `Command::new("cargo").args(["codesign", "--profile", "release"])`. Use it to reduce xtask maintenance if the distribution pipeline grows to include DMG or `.app` bundles. For v1.2 which only needs a signed binary + tar.gz for Homebrew Cask, the native-tools approach is simpler and has zero external tool dependencies.

### Critical signing flags

The existing `speck.entitlements` already has `com.apple.security.virtualization = true`. Two flags are **required** for notarization that ad-hoc signing currently omits:
- `--options runtime` — enables hardened runtime, mandatory for notarization
- `--timestamp` — uses Apple's timestamp authority, mandatory for the notarization ticket

### .pkg installer (BREW-DEVID-02)

`pkgbuild` and `productbuild` are Apple CLI tools available in Xcode CLT. Call from xtask via `Command` — no Rust crate needed.

## 5. Zeroize Registry Credentials — `speck-core`

### Problem

`RegistryAuth` in `speck-core/src/image.rs` holds `username: String` and `password: String`. The password is never zeroized from memory and can appear in debug output or core dumps.

### Recommended approach: `secrecy` 0.10.3

| Crate | Version | Purpose | Confidence |
|-------|---------|---------|-----------|
| `secrecy` | 0.10.3 | `SecretBox<S>` wrapper: zeroizes on drop, redacts Debug output, requires `.expose_secret()` | HIGH — verified crates.io Oct 2024; wraps `zeroize` 1.9.0 |
| `zeroize` | 1.9.0 | Underlying zeroization primitive (already a transitive dep via `sha2`) | HIGH — verified crates.io June 2026 |

### Why `secrecy` over bare `zeroize`

`zeroize` alone (`#[derive(Zeroize, ZeroizeOnDrop)]`) zeroes memory on drop but does nothing to prevent accidental logging (`{:?}`) or accidental clone. `secrecy::SecretBox<String>` adds:
- `Debug` impl prints `[REDACTED]` rather than the actual password
- No `Clone`/`Copy` derived — accidental duplication is a compile error
- Access requires `.expose_secret()` — creates an explicit audit point in `to_base64()`

```rust
// speck-core/src/image.rs
use secrecy::{ExposeSecret, SecretBox};

pub struct RegistryAuth {
    pub username: String,
    pub password: SecretBox<String>,
}

impl RegistryAuth {
    pub fn to_base64(&self) -> String {
        let json = serde_json::json!({
            "username": self.username,
            "password": self.password.expose_secret(),
        });
        BASE64.encode(json.to_string().as_bytes())
    }
}
```

`secrecy` has a `serde` feature for `Serialize` on `SecretBox` — use it only if `RegistryAuth` is deserialized from a config file. For the outbound-only `to_base64()` path, the feature is not needed.

```toml
# speck-core/Cargo.toml
[dependencies]
secrecy = "0.10"
```

## What NOT to Add

| Avoid | Reason | Use instead |
|-------|--------|-------------|
| `sled` (any version) | Pre-1.0; on-disk format unstable with no backward compat guarantee; last stable release September 2021; maintainer recommends SQLite for reliability | `rusqlite` + `deadpool-sqlite` |
| `sqlx` | Async macros require a live database connection at compile time; significant compile-time overhead; more machinery than three small tables in a single-writer daemon warrant | `rusqlite` + `deadpool-sqlite` (simpler, no macro magic) |
| `diesel` | ORM overhead; schema.rs + migration DSL heavier than needed for this use case | `rusqlite` + `rusqlite_migration` |
| `wiremock` | HTTP-level mock framework for HTTP servers — wrong abstraction layer; Docker API conformance tests belong in the `bollard`-based integration test (already in dev-deps) | `bollard` (already in stack) |
| `nix` | Broad syscall abstraction crate — not needed when only wrapping specific calls in vminitd behind a hand-rolled trait | Hand-rolled `Syscalls` trait + `libc` (already in stack) |
| `cargo-codesign` as a Cargo workspace dep | It is a CLI tool, not a library | Shell out to native Apple tools from xtask; optionally install cargo-codesign externally |
